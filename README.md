# NearCast

Android ↔ Android 局域网屏幕共享与远程触控，单 APK、无账号或云服务。

> **开发预览版 v0.2 / Draft PR #1**：代码通过 Android CI 编译，不代表通过双机真机测试。当前控制信令与媒体是**明文 TCP**（配对码不是加密协议），仅用于本人设备的可信隔离局域网，不能作为公网或生产可用软件发布。

## 功能

- Android NSD/mDNS 自动发现设备，手动 IP:端口连接后备
- 局域网六位验证码配对，同一 APK 兼具被控端和控制端
- MediaProjection + MediaCodec + SurfaceView 的硬件编解码链路
- 编码选择：H.264 / H.265 / AV1，优先选中模式，初始化失败自动回退 H.264；接收端必须具备对应解码器
- 分辨率：720p（长边 1280）、1080p（长边 1920）、原生（最高长边 4096）；实际按硬件能力自动回退
- 目标帧率：60 / 90 / 120 FPS；真实帧率依赖屏幕更新与 MediaProjection / MediaCodec 硬件实现
- **全屏观看**：隐藏系统栏，全屏按钮和退出全屏入口；保持原视频比例避免误触坐标偏差
- **网络协议可选**：TCP 稳定（默认）或 UDP 视频低延迟实验模式。UDP 将视频拆成 ≤1200 Byte 数据报，在 TCP 控制连接上交换接收端端口；丢包或解码依赖断裂时请求 IDR。音频、控制指令以及关键编解码参数集（SPS/PPS/VPS）仍走 TCP。UDP 不等于可靠无损，当前也未加密。
- **视频性能诊断与解耦**：视频网络接收线程不再直接等待 MediaCodec 输入缓冲，而是经有界解码队列交给专用解码线程；解码队列过载时申请新 IDR。TCP 发送队列与编码线程解耦，UDP 每帧复用分包缓冲。被控端显示**实际编码 FPS、物理/虚拟屏刷新率、编码码率、网络写出码率和队列深度**，控制端显示**解码提交/输出 FPS、接收码率、控制 RTT/抖动、解码排队与 IDR 请求**。最小化/恢复时重建解码器和重放参数集
- **系统声音（Android 10+）**：可选 AudioPlaybackCapture → PCM 48kHz/16-bit/mono → AudioTrack，使用用户明确授予的录音及屏幕捕获权限；仅能捕获允许共享的 MEDIA/GAME 音频，无法捕获通话、受保护/禁止捕获音频。此版优先可用性，尚未实现 Opus、音视频时钟同步和自适应抖动缓冲
- AccessibilityService 点击/滑动/返回/Home/最近任务
- 省电暗屏：最低亮度 + 显示保持唤醒，**不是真正的物理息屏**。部分 Android 系统锁屏将终止 MediaProjection

### 安装与构建

两台 Android 8+ 手机安装**同一版本的 APK**，连到互相可达的 Wi-Fi。
到 GitHub Actions 成功构建的工作流中下载 \`NearCast-debug\` artifact，解压并安装。

本地：Android Studio（JDK 17 / Android SDK 35），或 Gradle 8.10.2：

\`\`\`bash
gradle :app:assembleDebug
\`\`\`

### 操作

1. 打开两台手机 NearCast，控制端从附近设备列表选中被控端并输入六位配对码。
2. 被控端开始共享前选择编码、分辨率、FPS、是否共享声音；如果启用声音，先允许系统的录音权限弹窗。
3. 被控端允许系统屏幕采集，远程触控另外需要手动开启无障碍服务。
4. 控制端点击「全屏」切换沉浸显示，右上角可退出全屏。
5. 断开时主动「停止共享」释放媒体资源；音频开关的改变需要开启**新一轮**共享才能生效。

### 常见问题

- **从后台恢复时画面短暂黑屏**：需要 Android 恢复视频 Surface、解码器等待新 IDR；恢复时间受编码器关键帧生成及网络情况影响。若持续黑屏，复制日志并报告手机型号与 Android 版本。
- **闪断或跳帧**：TCP 模式 Wi-Fi 拥塞可能导致队头阻塞；队列溢出会丢弃旧 GOP 请求 IDR。UDP 模式降低 TCP 队头阻塞，但 Wi-Fi 丢包会触发重同步和跳帧。先用 720p / H.264 / 60 FPS 比较两种模式。丢帧/GOP 重同步计数仅覆盖本地发送队列过载，不代表网络全部丢包。
- **声音为空**：仅 Android 10+ 支持内部回放采集，需要授予 RECORD_AUDIO、MediaProjection 许可，且目标应用允许播放捕获。受保护视频、通话和一些游戏/音乐应用不会提供音频。
- **H.265 / AV1 没画面**：两台手机均需支持相应编码/解码，部分厂商声明支持但实际初始化失败；重新连接后选择 H.264。
- **旋转**：当前编码分辨率在开始共享时确定，旋转后的动态 VirtualDisplay resize 尚未实现，建议停止共享并重新授权。
- **网络协议说明**：现在可选 TCP 或 UDP 视频通道，当前 UDP 使用自定义分片头（非 RTP/QUIC，不兼容第三方播放器）；均尚未加密。发布前需要完善鉴权、SRTP/DTLS 或等效强加密、拥塞自适应、丢包恢复和时延测量；不能将实验版宣称为 120 FPS 稳定无损。
- **安全提醒**：PIN 只检查会话意图，不能防止 LAN 嗅探或中间人。当前测试版严禁公网部署及处理敏感数据。

## 编解码器主动探测与动态高刷（v0.3 测试版）

- App 启动后在后台扫描本机 H.264 / H.265 / AV1 的编码器和解码器、硬件加速属性、Surface 编码输入与 720p120 能力声明。
- 共享前点击「实测初始化」可进一步在后台执行 MediaCodec.configure / start；**不输入画面，也不保证持续编码帧率或低延迟**；共享期间禁用主动初始化测试以避免抢占硬件资源。
- 连接时接收端上报解码能力位图（NEARCAST/4，仅与同版本 APK 兼容）；被控端只会使用对端声明可解码的格式。
- AV1 不再自动选择软件编码器；只尝试有硬件加速声明的 AV1，无法初始化则依次尝试 H.265、H.264。某些硬件 AV1 实际编码延迟仍可能远高于 HEVC，建议优先使用 H.265。
- 编码时可选请求 KEY_LATENCY 和禁止 B 帧，OEM 可能忽略；运行时显示实际选择的编码器名称及参数。
- 新增物理/虚拟显示刷新率的持续监测和编码输出 PTS 帧间隔/抖动；第三方 App 改变刷新率时显示提示。
- UDP 接收端有短时间重排序窗口，减小偶发乱序导致的无意义 IDR；仍非完整的丢包恢复、拥塞控制或加密 RTP。

**重要系统限制：** Android 的屏幕刷新率是操作系统根据当前前台 App、设备设置和功耗状态选择的；公开 MediaProjection API 不能强制另一个 App 持续提供 120 FPS。也不应该插入重复帧以伪装真实 120 FPS。120Hz 终端显示和 120FPS 实时画面是两个不同指标。


## Wi-Fi Direct 无路由器直连（v0.4 测试）

本版本增加 Android Wi-Fi Direct (P2P) 的原生连接模式，**无需连接原有 Wi-Fi/路由器/公网**。它仍然建立局部 IP 网络并用现有 TCP/UDP 协议传流；无线干扰、MediaProjection 采集限帧、编解码队列仍会引起卡顿。

- 需要手机硬件支持 Wi-Fi Direct；在 Android 13+ 需要附近 Wi-Fi 设备权限，在 Android 12- 需要位置权限及启用系统位置服务。
- **被控手机**：打开 NearCast → 启用 Wi-Fi Direct → 「被控端建立直连」。组创建成功后，本机固定端口 39491 监听 NearCast；如果该端口被其它应用占用会提示不可建立便捷直连。
- **控制手机**：打开 NearCast → 启用 Wi-Fi Direct → 「控制端搜索」→ 点击找到的被控设备「加入」。部分厂商系统可能弹出组连接确认。
- 待状态变为「直连成功」后，点击「通过直连连接被控端」，输入被控手机的六位验证码。被控手机再手动授予录屏和辅助控制权限。
- 若直连组无法创建或系统拒绝权限，可继续使用原有局域网 mDNS/手动 IP 模式。旧版 APK 可能无法连接新版（NearCast 协议版本不同）。
- 建议在同一手机对上，固定 H.265 + 720p + 60FPS，分别测试已有 Wi-Fi 和 Wi-Fi Direct 两种连接，比较客户端 RTT、抖动、IDR 请求数与实际 FPS。
- **直连不保证提升帧率**：Android MediaProjection 和第三方 App 的 60Hz 限制仍存在；若编码端仅输出 60FPS，改变网络拓扑不会产生新的 120FPS 画面。
- 直连使用 Wi-Fi Direct 的链路安全机制，但当前 NearCast 应用层的 TCP/UDP 仍是未加密、未经强身份认证的测试协议；只能在用户授权的可信环境中使用，暂不可作为正式版本发布。

## AV1 探测修正

系统扫描会单独展示 AV1 **编码器**和**解码器**，不再因 720p120 未声明支持或系统未标记硬件加速就声称设备完全不支持 AV1。现在区分“系统提供解码器”“系统提供编码器”“Surface 编码输入”“系统硬件加速标志”“厂商实现但硬件属性未确认”“声明支持的 720p60 与 720p120”“初始化实测”。

测试版远控优先选择低延迟硬件/厂商编码器，软件 AV1 不自动使用。如果 AV1 初始化仍失败，将回退 H.265/H.264；真正是否适合低时延必须做持续编码和端到端时延实测。


## v0.5 — 简洁设备管理 / 客户端码率 / 软件优化

**界面：** 首页重构为「设备」「画质」「诊断」三个页面。设备中只显示配对、自动发现、手动 IP 与 Wi-Fi Direct 的引导式组建/加入；性能指标、编码探测和详细参数放到各自的设置页，避免堆叠。

**码率：** 控制手机在「画质」里设置 2–60 Mbps 的初始码率，也可在远程画面上点击「码率」实时调整。采用 \`NEARCAST/5\` \`SET_BITRATE\` 消息发送到被控端，调用 \`MediaCodec.PARAMETER_KEY_VIDEO_BITRATE\`，无需重建 MediaProjection。该值是*编码目标*，不是网络出口严格峰值整形；具体支持情况由手机厂商编码器决定。两端必须同版本。

**性能：** UDP 收包复用 ByteBuffer/DatagramPacket，分片过期检查降频，单帧只组装一次数据；静态画面不再每 800ms 强制 IDR；每帧 FPS 统计改为每秒汇报；远程观看可选择最低延迟的已解码输出帧丢弃，降低旧画面进入 Surface 排队的风险（并不丢弃压缩参考 P 帧）。保留诊断以区分编码输入/网络/解码/显示瓶颈。

设计思路与 Moonlight/Sunshine 对比见 [STREAMING_PERFORMANCE.md](docs/STREAMING_PERFORMANCE.md)。
